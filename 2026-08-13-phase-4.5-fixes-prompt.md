## Task A — CI is red; the site is not deploying

`e2e/gap/gap-flexibility.spec.cjs` → *"9. TTV chart canvas exists in DOM"* fails, on the first run
and on retry:

```
expect(locator('#gap-chart-ttv')).toBeVisible()
Expected: visible   Received: hidden
```

**The application is correct. The test is wrong.** Diagnosis, verified:

- The test loads `fixtures/gap-phase6.csv`. That fixture spans `10:00:00` to `10:00:05` —
  **six seconds** — so every record lands in one bucket.
- Its `Service` values are `SMS`, so nothing is a signing or a verification and **no pairs exist**.
  Time-to-Verify plots paired rows only, so it has no data by construction.
- Phase 4 Task D added `showChartMessage()`, which sets `canvas.style.display = 'none'` and shows a
  message instead. That is the specified, intended behaviour.

So the canvas is correctly hidden, and a test written before Phase 4 asserts it must be visible.

**Fix the test, not the feature.** The test's own name is *"canvas exists in DOM"* — existence, not
visibility. Assert that the chart card renders *something*:

```js
const canvas = page.locator('#gap-chart-ttv');
await expect(canvas).toBeAttached();
const msg = page.locator('#gap-chart-ttv').locator('xpath=..').locator('.chart-empty-msg');
await expect(canvas.or(msg)).toBeVisible();
```

Adjust to whatever locator strategy reads cleanest — the requirement is that the assertion passes
when the chart renders **and** when the empty-state message renders, and fails when neither does.

**Then check the other four charts** for tests making the same assumption. `gap-charts.spec.cjs` and
`gap-flexibility.spec.cjs` both predate Task D.

**Do not** weaken `showChartMessage()` or make the canvas visible-but-empty to satisfy the test.

## Task C — The chart screenshot does not show charts

`screenshots/capture-screenshots.cjs` contains:

```js
const charts = document.querySelector('.grid.grid-cols-1.lg\\:grid-cols-2');
if (charts) charts.scrollIntoView({ behavior: 'instant' });
```

That selector matches nothing in the current markup. The `if (charts)` guard swallows the miss, no
scroll happens, and `04-charts.png` captures the top of the dashboard — filters and tiles. I opened
it and confirmed.

So Phase 4 — the one entirely visual phase — shipped with no verified image of anything it changed.

**Fix, three parts:**

1. Point the scroll at a stable anchor. Use a `data-testid` on the chart grid container rather than
   a Tailwind class string; class-based selectors break every time the layout is touched, which is
   exactly what happened here.
2. **Remove the silent guards.** Every `if (el)` in this script should become "throw if missing".
   A capture script that quietly produces the wrong image is worse than one that fails.
3. **Capture against a fixture with real spread.** The script currently feeds an inline 20-record
   CSV covering seconds, so the charts sit in their empty state and the axis-crowding and encoding
   changes are invisible. Add a second capture pass using a multi-hour fixture — generate one if
   none exists — and save those as `11-charts-populated.png` and similar.

Then recapture and **look at the images**, not just the hashes.

## Task D — Four UI defects

### D1. Pairing-key remove buttons float over the modal header

Reported with a screenshot: the red ✕ badges from the Pairing Key section render on top of the
"Map CSV Columns" title when the modal body is scrolled.

**Cause:** in `renderPairingKeysUI()` the buttons are
`class="absolute -top-1.5 -right-1.5 ... z-10"`. They are positioned outside their parent's bounds
and carry a `z-10` that competes with the modal header, and the scroll container does not clip them.

**Fix — preferred:** stop using a floating badge. Put the remove control **inside** the flow — a
small ✕ at the right-hand end of each pairing-key row, in normal document flow, styled as a muted
glyph that brightens on hover. This removes the stacking problem entirely and fixes a second issue
raised in the earlier UI review: bright red filled circles overlapping a form control read as error
badges, not as delete affordances.

**Fix — minimal, if the above is too large:** give the scrollable modal body `position: relative;
overflow: hidden` on the appropriate wrapper and raise the header's `z-index` above the badges.
This is a patch; the badges will keep causing trouble.

### D2. Dropdowns need one padding rule, and currently have none

Reported: text now sits too close to the border. Historically the chevron was too close; that was
fixed, and the text problem appeared.

**Cause, verified:** `.atlas-select` sets `padding-right: 2rem` and **no other padding**. No
`padding-left`, no vertical padding. A previous change removed the Tailwind `px-*` utilities from
these elements "to let `.atlas-select` handle padding" — but the class never took over the job.
Left padding is now whatever each element happens to inherit, which is why it varies across the
module.

**Fix — establish the rule in one place:**

```css
.atlas-select {
  padding: 0.5rem 2rem 0.5rem 0.75rem;   /* right leaves room for the chevron */
}
.atlas-select.atlas-select-sm {
  padding: 0.25rem 1.75rem 0.25rem 0.625rem;
  background-position: right 0.45rem center;
}
```

Then:

- Remove every `px-*`, `py-*`, `pl-*`, `pr-*` and `p-*` utility from elements carrying
  `.atlas-select`, in both the HTML and the JS template literals that build selects.
- Replace the ad-hoc `py-1 text-xs` on the chart series and bucket dropdowns with
  `.atlas-select-sm`.
- Add a line to `docs/SPEC.md` §9 "Add a select": **padding on selects is owned by `.atlas-select`
  and its size modifier. Never set padding on the element.** The existing note says not to use
  Tailwind utilities but does not say who owns padding, which is how this recurred.

Verify with the screenshot set before and after — this touches every dropdown in the module.

### D3. Column filters apply before anything is entered

Reported: opening a column filter and clicking the control — without typing or selecting — causes
the table to filter.

**Partly diagnosed; reproduce before fixing.** Two concrete defects found by reading
`syncFromColFilter()`:

1. **No `NaN` guard on the time filter.** The `time` branch does
   `new Date(fromEl.value).getTime()` and assigns the result to `gapTimeFrom` with no validity
   check. Any value the browser reports that does not parse yields `NaN`, and every subsequent
   comparison against `NaN` is `false` — which silently excludes rows. Guard it: assign `null`
   unless the parsed value is a finite number.
2. **The `time` branch returns early**, skipping the `closeAllColDropdowns()` that every other
   branch runs. So time behaves differently from every other column filter.

`datetime-local` inputs also emit `change` during picker interaction in Chromium — including from
the picker's own Clear and Today controls — so a user who opens the calendar and clicks around
without committing a value can trigger a filter pass.

**Required approach:** reproduce first with the console open, and record which event fires from
which control. Then make `syncFromColFilter()` a no-op when the control's value is unchanged from
its current state. Do not guess at a fix and ship it — this is a behaviour report, and the value of
the fix depends on the actual trigger.

Add a Playwright test: open each column filter dropdown, click its control, dismiss without
entering anything, and assert the row count is unchanged.

### D4. The date/time picker does not match the theme

Reported: the calendar and time selector look wrong against the dark UI.

**Be honest about the ceiling here.** `datetime-local` renders a **native browser picker**. It is
almost entirely unstyleable — `color-scheme: dark` (already set) and `accent-color` are effectively
the whole surface. The blue selection highlight and the light time column are Chromium's, not the
app's.

**Do this much now:** set `accent-color: var(--gap-accent)` on the date inputs so the selection
highlight is violet rather than browser-blue. Confirm `color-scheme: dark` is actually applying to
these inputs specifically.

**Then stop.** Anything further means replacing the native picker with a custom component — a real
piece of work with accessibility and keyboard-handling implications. If the result still looks off
after `accent-color`, report that and leave it for a scoped decision rather than starting a custom
picker inside this task.

## How this project has failed before

You do not have access to the project's memory document. These patterns have each recurred.

**Tests that assert nothing, and suites reported green without being run.** Six Playwright tests
once re-implemented application logic and asserted against their own copy while the suite reported
"182 passing". A later file asserted `expect(40 + 60).toBe(100)`. Phase 4 reported all-green with a
different test failing in CI. **Run it. Paste the real output.**

**A claimed blocker is a claim like any other.** Phase 3 skipped screenshots because the tooling
"was deleted" — it was present the whole time. Verify the obstacle before reporting it.

**Guards that swallow missing elements.** `if (charts) charts.scrollIntoView(...)` is why the chart
screenshot has been wrong. Four earlier tests hid missing elements behind
`if (await ….isVisible().catch(() => false))`. **A missing element is a failure, not a branch.**

**Fixes land one condition too narrow, or relocate the bug.** A toast merge missed a third call in
the same function; a country-code fix moved its own defect into the tooltip. **Read the whole
function, and ask where else the thing you just fixed now lives.** For D2 specifically: selects are
built in HTML *and* in JS template literals — fix both.
