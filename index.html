What Is This Tool?

This tool helps you figure out where to place your infrastructure ("cells") around the world so that your endpoints get fast, reliable connections.

You tell the tool:

  • Where your existing cells are today
  • Where your endpoints are located
  • What latency (in milliseconds) you promised them in your SLA
  • Optionally, how much your current cells cost per month

The tool then uses realistic distance parameters and a 32x32 AWS latency matrix to recommend exactly where to deploy new cells — optimizing to strictly meet your SLA for the lowest possible cost.

Key Concepts

Cell

A server or piece of infrastructure you deploy in an AWS data center.

Endpoint

An integration partner, service consumer, or client application that needs to connect to your cell.

SLA (Service Level Agreement)

The maximum latency (in milliseconds) you've promised your endpoints.

Latency

The round-trip time (in milliseconds) for data to travel from your cell to your endpoint and back.

1 Current Footprint

Tell the tool where you already have cells deployed. This is optional.

Use List View to browse regions by continent, or Map View to visualize your selections.

Below the cell selection, you'll find the Infrastructure Cost Profile accordion — see the next section for details.

Cost Calculator

The cost calculator is optional but powerful. It lets you estimate the monthly OPEX impact of deploying new cells.

The "Hidden Global Index"

The tool has a hardcoded AWS Regional Price Index anchored to US East (N. Virginia) = 1.00x. Every other region is priced relative to it:

US East (Virginia)1.00x
Europe (Paris)1.10x
Asia Pacific (Tokyo)1.25x
South America (São Paulo)1.50x
Africa (Cape Town)1.30x
Middle East (Dubai)1.25x

Reverse-Engineering the Global Base

When you input a cost for Paris ($2,674), the tool knows Paris is 1.10x. It reverse-engineers the normalized base:

$2,674 ÷ 1.10 = $2,430 (True Global Base)

Blended vs. Specific Baseline

  • Blended: Averages reverse-engineered base costs from all inputted cells.
  • Specific: Anchors to one specific cell of your choice.

How It Works Under the Hood

Coverage-First Algorithm with SLA Safety Floor

The tool uses a coverage-first greedy algorithm. Placement quality outranks cost. Each iteration:

  1. Eligibility gate: A (region, endpoint) pair is eligible only if headroom = SLA − latency ≥ safetyFloor. The safety floor (default 20ms) ensures no marginal passes.
  2. Selection priority: Among regions covering ≥1 eligible uncovered endpoint:
    • 1st: MAX endpoints covered (breadth first)
    • 2nd tie-break: MAX minimum headroom across covered endpoints
    • 3rd tie-break: MIN region cost
  3. Remove covered endpoints; repeat until nothing more can be covered.

Marginal bucket: Endpoints with no eligible region but passing at headroom < safetyFloor are flagged as marginal — not impossible, but requiring SLA relaxation. Existing cells still cover endpoints even below the floor (flagged marginalExisting), but new recommendations apply the floor strictly. The latency matrix is noisy (asymmetric by up to ~30 ms), so single-millisecond figures are indicative; recommendation cards show a latency band and confidence chip instead of a false-precise point.

Legacy Mode

Set the safety margin to 0ms to restore classic pass/fail SLA behavior with cost-per-customer scoring.

Latency Model

One unified model — no mode selector:

  • AWS region or resolved city (within 50 km): Uses the measured backbone matrix directly. This is the most accurate path.
  • Unresolved city (no region within 50 km): Haversine distance × 0.012 ms/km + infrastructure tier tax (Tier 1: +5ms · Tier 2: +20ms · Tier 3: +40ms · Tier 4: +60ms).

Adding the same city from the World Cities tab, the AWS Regions tab, or by clicking on the map all produce identical latency — the tool resolves to the same region.

Why 0.012 ms/km? (The Physics)

This propagation delay factor is mathematically grounded in the physics of fiber optic networking:

  • Speed of light in a vacuum: ~300,000 km/s.
  • Speed of light in glass (fiber): ~200,000 km/s (due to a refractive index of ~1.5).
  • Time per kilometer: 1 km / 200,000 km/s = 0.000005 seconds, or 0.005 ms per km.
  • Round-Trip Time (RTT): Networking latency measures the time to go and come back. Doubling the one-way time: 0.005 ms × 2 = 0.01 ms per km.
That's it!

Green-Plan What-If

After running a coverage analysis, the dashboard shows a "What-if: Make Everything Green" section. This tells you exactly how much you'd need to relax your SLA to eliminate all marginal and impossible endpoints.

Two modes

  • Global: One relaxed SLA for all endpoints. Simple — just raise the SLA threshold and everything turns green.
  • Per-Endpoint: Each endpoint gets its own minimal relaxation. More precise — some endpoints need only 5ms more, others need 50ms.

The section also shows the extra OPEX — the cost difference between your current plan and the green plan.

Saved Scenarios

On the SLA Configuration step (step 3), you'll find a Saved Scenarios section. Save your current analysis configuration — endpoints, SLA, safety floor, footprint, costs — and reload it later.

Important: Scenarios are stored in your browser's localStorage. They are per-machine — if you switch browsers or clear your browser data, scenarios are lost. Use session JSON export for portable backups.

Share Report

On the Coverage Analysis dashboard (step 4), click "Share Report" to download a standalone HTML file. This file contains all your analysis results — endpoints, coverage, recommendations, costs — in a self-contained format.

The report opens in any browser with no internet connection required. Share it with stakeholders who don't have access to ATLAS.

What Is This Tool?

The Onboarding Cost Calculator scopes out the engineering hours and timeline required to bring a new customer online.

It acts as an "MS Project" style interactive grid, generating a Financial Quote (Internal Cost + Customer Price) and an Interactive Project Timeline all in one unified view.

Deployment Scopes (Tiers)

The onboarding effort scales based on the infrastructure and integration requirements for the specific customer. Select the appropriate tier from the top ribbon to load the default task template.

  • Tier 1: Full Deployment (New Cell + New Provider) — The heaviest lift. Requires standing up new AWS infrastructure, building initial API handshakes with a new service provider, and running full security validation.
  • Tier 2: Integration Only (Existing Cell + New Provider) — Uses existing infrastructure in the region, but requires establishing API handshakes and security posture with a new service provider.
  • Tier 3: Standard Onboarding (Existing Cell & Provider) — The lightest workload. The cell and provider are already established. Focuses purely on QA, training, and cutover for the new end customer.
Warning: Resetting Timeline
Changing the Deployment Scope tier will ask for confirmation before resetting your entire timeline to the default template for that tier. Save your work (Export JSON) before switching if you want to keep custom tasks!

How the Math Works

The 4-Hour Ceiling Rule

Project estimation must be realistic. If you type "17" hours into the grid, the calculator automatically snaps it to 20 hours. We strictly enforce a 4-hour (half-day) minimum increment for all scoping to avoid messy fractions.

Financial Formulas

Internal Cost = Total Hours × Blended Hourly Rate
Customer Price = Internal Cost ÷ (1 - Margin %)

Interactive Gantt Features

The unified grid on the left and the chart on the right are perfectly synced.

  • Drawing Dependencies: Hover over a blue task bar. Grab the small circle at the end of the bar and drag it to the start of another task to draw a dependency arrow.
  • Deleting Dependencies: Double-click on any green dependency arrow to delete it.
  • Generic Calendar: The top scale abstracts real-world dates (ignoring weekends) into clean "Day 1, Day 2" progression blocks for pristine scoping.

Dragging to Resize Tasks

You can grab the edge of any blue task bar and stretch it. What happens next depends on the Link Duration to Cost checkbox in the top ribbon:

Linked (Checked)
Stretching a task from 2 days to 3 days adds billable hours (e.g., jumps from 16h to 24h) and automatically updates the input grid. Your total project cost and invoice price will immediately increase.
Unlinked (Unchecked)
Stretching a task from 2 days to 3 days simply means the resource is working part-time. The billed hours and financial cost remain perfectly locked.

What Is the Call Auditor?

The Call Auditor helps Network Operations and Monitoring teams analyze EDR (Event Detail Record) call data to identify discrepancies between Signing and Verification requests, with built-in UK destination number validation.

Upload a CSV export of your call records, map the columns, and the tool automatically computes metrics and generates time-series visualizations — all in your browser with no data sent to any server.

Upload & Column Mapping

Click the Upload CSV button or drag-and-drop a file onto the drop zone. ATLAS auto-detects columns by matching CSV headers against expected field names (e.g., "Time", "Service", "Source IP"). If auto-detection fails, use the manual Column Mapping dropdowns to assign each required field.

Required Columns
At minimum you need a timestamp, a service type (signing / verify), a destination number, and a status field. Optional columns include source IP, processing time, and customer name.
Excel Tip
Format phone number columns as Text before exporting. Excel converts long numbers to scientific notation (e.g., 4.47305E+11), which truncates digits. ATLAS can recover the + prefix stripped by Excel, but cannot restore lost precision.

Dashboard Metrics

After analysis the top row of cards summarises your dataset:

  • Total Records — rows parsed from the CSV.
  • Signing / Verification — split by service type.
  • Destination Issues — destination numbers are categorised three ways: Malformed (fails E.164 structure), Non-UK (valid number, wrong country code), and Suspected (passes structure but shows repeated or sequential digits). A breakdown panel with clickable reason chips appears below the tiles when issues are present.
  • Processing Time Outliers — rows exceeding the processing-time threshold (configurable in Settings, default 100ms).

Below the metric tiles, the Call Pairing panel shows match-rate statistics, unverified/unsigned counts, and time-to-verify percentiles. Click the red/amber/gray blocks to filter the table. The pairing panel is global (whole dataset) and does not recompute on filter changes.

Click any metric card to filter the data table. Click again or use Reset Filters to clear.

Data Table

The paginated table shows individual call records with a Pair column indicating match status. Columns are sortable by clicking the header. Use the filter bar to narrow results by service, status, customer, destination, processing time range, or pair status.

  • Pair ID — paired pills display their pair ID (e.g. P3 · Paired); orphan pills show status text only.
  • Hover highlight — hovering a paired row highlights its partner (violet ring) and dims other rows. If the partner is on another page, the pill tooltip notes (partner on page N).
  • Group by pair — a sliding switch next to "Rows per page" groups rows by pair. Paired rows render contiguously with a subtle alternating band; orphans render as single-row bands. Groups are paginated (the indicator shows A–B of G groups (R rows)) and sorted by the signing row's column value. The page-size label switches to "Groups per page" while grouped.

Call Pairing

The Call Pairing panel matches signing requests to their corresponding verification requests using a heuristic: same from and to numbers within a directional time window (configurable in Settings, default 1000ms).

  • Algorithm — first-in-wins (FIFO): each verification pairs with the earliest unmatched signing within the window; signings older than the window are evicted as unverified; superseded retries are flagged duplicate.
  • Pair statuses: Paired (green) = signing matched to a verification; Signed · not verified (red) = signing with no verification in the window; Verified · not signed (amber) = verification with no preceding signing in the window; Unpairable (gray) = missing or invalid timestamp.
  • Match rate = paired outcomes / (paired + unverified + unsigned). The time-to-verify median and P95 help calibrate the window.
  • Global panel — the pairing panel shows whole-dataset stats and does not change with table filters.

Visualizations

Below the table you will find four charts:

  • Invalid Numbers Over Time — line chart of invalid destination counts per time bucket.
  • Signing vs Verification Volume — stacked bar chart. Each service type has its own bar, internally stacked: valid requests (blue/green) on the bottom, invalid destinations (orange) on top.
  • Processing Time Distribution — line chart of average processing latency per time bucket. The Y-axis scales dynamically to the data range.
  • Time to Verify Over Time — dual-line chart showing median TTV (cyan) and P95 TTV (pink dashed) per time bucket, computed from paired signing/verification calls.

Each chart has its own Time Bucket dropdown (Auto / 1 Min / 5 Min / 1 Hour / 1 Day) in its card header for independent bucketing.

UK Number Validation

Every destination number is validated against UK formatting rules:

  • Format — must start with +44. Scientific notation (e.g., 4.47305E+11) is auto-converted. The + prefix stripped by Excel is restored automatically.
  • Length — total digits must be 11–13 (including country code).
  • Prefix — first digit after +44 must be 1, 2, 3, 7, or 8.
  • Pattern — rejects numbers with all identical digits or runs of 5+ sequential digits (e.g., +447123456789).
