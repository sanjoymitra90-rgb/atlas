## 1. How this project fails — read before you write anything

These are not general good practices. Each one has cost this project a shipped defect, and at least
two of them are directly relevant to the work below.

- **A fix lands in one of two identical branches.** `renderGapTable()` has a grouped path and a flat
  path. Task A exists *because* a previous fix went into only one of them. Check both. Every time.
- **A test that cannot fail is worse than no test**, because it stops anyone looking. Before you
  claim a new test works: break the thing it names, run it, watch it go red, put it back. State that
  you did this in the commit message.
- **"All tests pass" can mean "on my machine".** A green suite is evidence about the *environment*
  it ran in. Timezone, locale and clock are hidden inputs. CI runs UTC and nothing else, so any bug
  where UTC and the correct answer coincide is invisible there. This is the entire subject of Task B.
- **Documents drift and agents build on them.** `SPEC.md` currently describes three defects that are
  fixed and one function signature that does not exist. Fix the document in the same commit as the
  code it describes — never in a batch at the end, from memory.
- **When a test depends on a harness doing something, assert that the harness did it.**
  `src/auditor/time.test.js` already does this and it is the pattern to copy in Task B.

## 2. Task A — Invalid timestamps must sink to the bottom in *both* table modes

### A1. The defect

`SPEC.md` invariant 8 states that a row with `timeValid === false` *"always sorts to the bottom
regardless of direction."*

`renderGapTable()` sorts in two places. The **flat** branch honours the invariant — it tests
`timeValid` before applying direction. The **grouped** branch (group-by-pair mode) does not test
`timeValid` at all. It compares `repA.timestamp || 0` against `repB.timestamp || 0`, and an
unparseable row has a null timestamp, so it becomes `0`.

Descending, `0` lands last and the invariant appears to hold. **Ascending, `0` lands first** — the
rows the user can trust least appear at the top of the page.

### A2. Reproduce it before you fix it

Lift both comparators out of `index.html` into a scratch file and run them over a five-row array
containing three parseable rows and two with `timestamp: null, timeValid: false`. Print the row
order for all four combinations (flat/grouped × ascending/descending). Three orders put the invalid
rows last; grouped-ascending puts them first. **Put that table in your hand-back.**

Do this before changing anything, and again after.

### A3. The fix

Give the grouped comparator the same `timeValid` precedence the flat one already has, applied
before direction is considered. Do not restructure either comparator beyond that — the rest of both
is correct.

Then ask the question this project keeps failing to ask: **where else does the thing you just fixed
live?** The grouped comparator also handles `pairStatus` and `ukCategory` columns. Check whether
invariant 8 should apply when sorting by those columns too, and say what you concluded either way.

### A4. The test

An e2e test in `e2e/gap/` that loads a fixture containing at least one unparseable timestamp,
switches on group mode via `gap-group-toggle`, sorts by time **ascending**, and asserts the amber
invalid rows are the last rows in the table body.

`fixtures/gap-core.csv` has one unparseable row; `fixtures/gap-invalid-only.csv` has two. Confirm
which produces the arrangement you need by running it, not by reading the file.

Prove the test fails: revert your fix, watch it go red, re-apply.

## 3. Task B — Make the bucketing code timezone-provable

### B1. Why this is here

Phase 4.8 fixed a timezone bug in `src/auditor/time.js` and added a genuinely good test for it —
one that spawns child processes under two forced timezones and compares results.

`src/auditor/buckets.js` sits directly downstream. It decides which hour or day each chart bar
belongs to. It currently uses `getUTCFullYear`, `getUTCMonth`, `getUTCDate`, `getUTCHours` and
`getUTCMinutes` throughout, which is **correct**. Nothing tests that it stays correct.

Demonstrated: changing a single `getUTCHours()` to `getHours()` in `formatBucketLabel()` leaves the
full 85-test suite **green under `TZ=UTC`** and fails 3 tests under `TZ=Asia/Dhaka`. CI sets no `TZ`
and GitHub runners are UTC, so that change would deploy.

This is the same shape as the Phase 4.8 defect, in the module next door, and the charts are exactly
what it would corrupt.

### B2. What to add

Timezone-independence tests for `src/auditor/buckets.js`, covering `getGapBucketKey()` and
`formatBucketLabel()` across all four intervals (`1min`, `5min`, `1hour`, `1day`).

**Copy the mechanism already in `src/auditor/time.test.js`** — child processes under forced `TZ`
values, results compared. Do not invent a second approach; one harness the project already trusts
is worth more than two it has to reason about.

Include the self-verifying assertion that harness has: something *known* to be timezone-dependent
must **differ** between the two zones, so the test goes red if the harness ever stops actually
varying the timezone. Without it the whole thing passes vacuously the moment the mechanism breaks.

Choose a timezone with a non-zero offset **and** one that shifts the calendar date for at least one
of your inputs — a bucket key crossing midnight is where this class of bug actually bites.

### B3. Also fix the environment, not just the test

Add `TZ` variation to how the suite is invoked, so this class of bug cannot hide in CI again:

- a script in `package.json` that runs the unit suite under a non-UTC timezone
- a step in `.github/workflows/deploy.yml` that runs it

Keep the existing UTC run. The point is that both run, not that one replaces the other.

### B4. Prove it

Break `buckets.js` the way §B1 describes, show the new test failing, put it back. State this in the
commit message.

## 4. Task C — Three untested paths

Each of these was found by deliberately breaking working code and observing that the suite stayed
green. None is a bug today. All three are places where a future edit lands silently.

### C1. Contingency money path — `src/onboarding/financials.js`

`computeOnboardingFinancials()` adds contingency hours into `billableHours`, and `internalCost` is
derived from `billableHours`.

Changing `internalCost` to derive from `totalHours` instead — dropping contingency out of the
customer's price entirely — **breaks nothing.** Every existing test either passes
`contingencyPct: 0` or asserts only `contingency` / `contingencyHours`, never the money.

This is a quoting tool. The untested path is the one that decides what a customer is charged.

Add tests asserting `internalCost` and `customerPrice` with a **non-zero** contingency, including
the interaction with margin.

### C2. `src/optimizer/geo.js` has no test file

`haversine()` is the only export and there is no `geo.test.js`. Changing the Earth's radius from
`6371` to `1` leaves the suite green.

It underpins invariant 1 (the light-in-fibre floor), the 50 km region-resolution threshold in
`resolveCityToRegion()`, and the direct-path latency estimate. The R5 physics test in
`e2e/optimizer/opt-review.spec.cjs` re-implements haversine inside `page.evaluate()` rather than
calling this one — so it checks the *matrix data* against physics, and never checks this function.

Add `src/optimizer/geo.test.js` with known great-circle distances between real city pairs, a
symmetry check, and the zero-distance case.

### C3. BOM stripping — `src/auditor/parse.js`

`parseGapCSV()` strips a leading byte-order mark. `SPEC.md` documents it. Removing the line leaves
the suite green. Add a test that feeds a BOM-prefixed CSV and asserts the first header is clean —
a BOM here corrupts the first column name, which breaks column mapping for every downstream step.

## 6. Task E — The two open display questions (only if the maintainer has answered)

**Do not guess on these. If §6 of your instructions has not been filled in with a decision, skip
this task entirely and say you skipped it.**

Both are Phase 4.8 acceptance criteria that were not met, and both were reported rather than fixed
because the right answer is a product call.

### E1. Display format

The Time column renders `2026-01-15 10:30:00` where the source said `2026-01-15T10:30:00Z`. Same
instant, same clock time, normalised format. The Phase 4.8 spec had said displayed text must be
unchanged for `Z`-suffixed rows, so this is a deviation.

- **Option "keep"** — normalised display is consistent across every source format. Document the
  deviation in `SPEC.md` §7.2 and close it.
- **Option "revert"** — echo the source string verbatim when the instant is unchanged, and render
  normalised UTC only where a conversion happened.

### E2. The tooltip fires on unchanged rows

In `formatGapTimeCell()`, the "did this change?" test is a string comparison:
`utc !== raw && utc + 'Z' !== raw`. For `2026-01-15T10:30:00Z` the rendered value is
`2026-01-15 10:30:00` — textually different (`T` versus space) though the clock time is identical —
so the tooltip fires on rows where nothing was converted.

The correct fix depends on E1. Under "keep", compare **instants** rather than strings: re-parse the
raw value and show the tooltip only where the parsed instant differs from what a naive reading of
the source would suggest. Under "revert", the problem largely dissolves.

Whichever lands, add a test asserting a `Z`-suffixed row carries **no** tooltip and an offset-bearing
row **does**.
