## 3. Task A — Extract and test timestamp parsing

**Third time of asking. Do not defer it again; if you cannot, say so explicitly and stop.**

### A1. Where the logic is

Timestamp parsing lives inline inside the row-mapping function in `index.html` — the block that
produces `timestamp`, `timeValid` and `timeHadOffset` from `rawTime`. It handles four cases in
order:

1. a 10-digit string → epoch **seconds**, multiplied by 1000
2. a 13-digit string → epoch **milliseconds**
3. `D/M/YYYY H:MM(:SS)` → `Date.UTC(...)`
4. anything else → `new Date(trimmed)`, with `timeHadOffset` set from a `Z`-or-`±HH:MM` test

Phase 4 changed how every timestamp in the application is interpreted, and none of this is covered
by a test.

### A2. Extract it

Move it to `src/auditor/time.js` as a pure function — suggested shape:

```js
export function parseGapTimestamp(raw) // → { timestamp, timeValid, timeHadOffset }
```

**This is a move, not a rewrite.** A reviewer must be able to diff the old inline body against the
new function and see only the change of location and the addition of `export`. Update the call site
to use it and expose it through the existing bridge in `src/main.js` alongside the other modules.

Do not change behaviour in this commit. A2 and A4 are separate commits.

### A3. Unit tests

In `src/auditor/time.test.js`, covering at minimum:

- a 10-digit epoch, asserting the value is multiplied by 1000
- a 13-digit epoch, asserting it is not
- an ISO timestamp **with** an offset — both `Z` and `+05:30` — asserting `timeHadOffset` is true
- an ISO timestamp **without** an offset, asserting `timeHadOffset` is false
- a `D/M/YYYY H:MM` value, asserting the day and month land the way the code actually reads them
- an unparseable value, asserting `timeValid` is false and nothing throws

**Run the function against a table of inputs and print the results before you write the
assertions.** Record what it actually does; do not write the expected values from this document.
If any behaviour surprises you, report it rather than encoding it silently.

### A4. A defect to fix, with a test first

`timeHadOffset` is set only in the fourth branch. **A 10- or 13-digit epoch therefore reports
`timeHadOffset: false`** — and the app counts rows where `timeValid && !timeHadOffset` to decide
whether to warn the user that timestamps carried no timezone and were assumed UTC.

An epoch value is unambiguous. There is no assumption to disclose. So a file of epoch timestamps
triggers a warning about an assumption that was never made, and inflates the count in it.

**Fix:** epoch inputs should report `timeHadOffset: true`, or the flag should be renamed to what it
actually means and the warning condition adjusted. Prefer whichever makes the warning correct with
the smaller change, and say which you chose and why.

The `Date.UTC` branch is a genuine assumption and should keep reporting `false`.

### A5. A cross-check test

Add a Playwright assertion that a known fixture row shows **the same hour in the table cell as on
the chart axis**. Phase 4's whole timezone item was that these two disagreed. Pick a fixture row
whose hour is unambiguous and assert both.

### A6. Report, do not fix — the date-order ambiguity

The `D/M/YYYY` branch reads `01/02/2026` as **1 February**. A CSV exported by a US-configured tool
means 2 January, and the app will silently misplace every row by up to eleven months.

**Do not change this.** Note in your hand-back what the current behaviour is and that no signal
distinguishes the two formats. It is Sanjoy's call whether to detect, ask, or document it.

## 4. Task B — The staleness guard

Phase 4.6's F1 landed: every npm test script now builds first. F2, F3 and F4 did not. F1 alone was
explicitly described in that spec as insufficient, because `npx playwright test`, an IDE runner or a
hand-written CI step all bypass npm.

`e2e/global-setup.cjs` currently contains only the CDN dependency check.

### B1. Fail if the build is missing or stale

Before the existing CDN check, in `globalSetup`:

1. **Fail if `dist/index.html` does not exist.**
2. **Fail if `dist/index.html` is older than the newest of `index.html` and everything under
   `src/`** — `.js` and `.css`. A change to `src/auditor/validate.js` invalidates the build just as
   surely as a change to `index.html`, and unit tests import `src/` directly so they would not
   catch it.

Compare `mtimeMs`. Throw from `globalSetup` so the run aborts before any test executes. **No new
dependencies** — a recursive `readdir` and a max is enough. The message must say what to do:
`dist/index.html is stale (src/auditor/time.js is newer); run npm run build`.

### B2. Prove the guard fires

Touch `index.html` without changing its content, run `npx playwright test` directly — not through
npm — and confirm the run aborts with the stale-build message **before any test runs**. Then build
and confirm it proceeds.

**State in the commit message that you did this and what you saw.**

### B3. Explain it in `DEPLOY.md`

Two or three sentences in that file's plain register: the tests run against the built copy rather
than the source, every test command now rebuilds automatically, and if something bypasses that the
tests refuse to run rather than silently checking an old version.

No jargon without a gloss. That file is written for a non-developer.

## 5. Task C — The screenshot harness photographs the wrong fixture

`e2e/screenshot.js` uploads `fixtures/gap-core.csv`. That fixture has **five signings and zero
pairs**, so all three timing charts render "No paired calls in the current view." instead of a
chart.

Phase 4.6 added two of those three charts. **The tool that exists to verify visual work cannot show
the newest visual work.**

### C1. Point it at the populated fixture

Use `fixtures/gap-screenshots.csv` — 63 rows, same-second signing/verification pairs, 30 of 32
signings pairing within the default 1000ms window, a mix of valid and invalid destinations spread
across several hours. It was rebuilt for exactly this purpose in Phase 4.6 and nothing currently
uses it.

**Confirm before relying on it:** load it and read `gapPairSummary.pairedPairs`. Assuming a fixture
pairs, rather than checking, is a mistake this project has made more than once.

After the change, open both screenshots and confirm all seven charts are drawn — not just that the
files changed. **Hash them too**: identical hashes across a fixture change means the capture did not
take.

### C2. Keep the output out of the repository

`screenshot-gap-dark.png` and `screenshot-gap-light.png` are written to the repository root and are
**not** ignored. The next `git add .` publishes them. Add them to `.gitignore` — a pattern covering
`screenshot-*.png` at the root, so future captures are covered too.

### C3. Report, do not fix — the lost coverage

The harness previously produced eleven captures: gateway, upload prompt, mapping modal, dashboard,
charts, table, settings modal, export modal, grouped view, pair panel, full page. It now produces
two full-page shots, dark and light.

The consolidation fixed a real problem — the old script targeted the unbuilt source and swallowed
seven failures — and two full-page captures at the right fixture do cover the charts, tiles, table
and filter bar in one image.

**What is no longer covered: the two modals, the grouped view and the pair panel**, none of which
appear on the main page.

Do not rebuild them. State the trade-off in your hand-back so Sanjoy can decide whether it matters
before Phase 5, which is the layout and density phase and will touch modals.
