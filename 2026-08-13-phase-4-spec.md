## 2. Task A — Legend colour collision (bug)

**Where:** `renderGapCharts()` and `renderSingleChart()`, the Signing vs Verification Volume
dataset definitions.

Four datasets, three colours. Verified in the current source:

| Dataset | backgroundColor | borderColor |
|---|---|---|
| Signing (Valid) | `rgba(59, 130, 246, 0.7)` | `#3b82f6` |
| Signing (Invalid) | `rgba(245, 158, 11, 0.7)` | `#f59e0b` |
| Verification (Valid) | `rgba(16, 185, 129, 0.7)` | `#10b981` |
| Verification (Invalid) | `rgba(245, 158, 11, 0.7)` | `#f59e0b` |

The two invalid series are byte-identical. In a stacked bar with two stacks, the user cannot tell
signing-invalid from verification-invalid. The legend shows four entries and the chart shows three
colours.

**The underlying problem is that colour encodes two variables at once** — service *and* validity —
with no system. Fix the system, not just the clash.

**Required approach:** hue carries service, treatment carries validity.

- Signing (Valid) — `#3b82f6` at 0.7
- Signing (Invalid) — same hue, visibly lighter and desaturated (e.g. `rgba(147, 197, 253, 0.75)`)
- Verification (Valid) — `#10b981` at 0.7
- Verification (Invalid) — same hue, visibly lighter and desaturated (e.g. `rgba(110, 231, 183, 0.75)`)

This keeps each stack readable as one service, makes the valid/invalid split legible within it, and
frees amber for its existing meaning elsewhere in the module. If the invalid tones are hard to
separate from their valid counterparts at small bar widths, add a 1px darker border rather than
changing hue.

**Test:** assert programmatically that the four datasets have four distinct `backgroundColor`
values. A single assertion prevents this whole class of bug returning.

## 3. Task B — Table and charts disagree about time (bug)

**Where:** `renderGapTable()` Time cell; `getGapBucketKey()` and `formatBucketLabel()` in
`src/auditor/buckets.js`; the timestamp parsing block in `processGapData()`.

`formatBucketLabel()` is consistently UTC — it uses `getUTCMonth()`, `getUTCHours()`, and for the
minute intervals it slices the bucket key string directly. That is correct and should not change.

The table prints `row.time`, the **raw CSV string**, unmodified.

When the source carries an explicit offset (`2026-08-11 20:50:19.588 +00:00`) the two agree. When
it does not (`2024-01-15 10:00:40`), `new Date()` parses it as **local time**, stores a UTC
timestamp, and the chart axis then displays a value differing from the table by the viewer's offset.
Observed in practice: table showing `10:00:40`, chart axis showing `4:00 AM`, on the same record.

Two records with the same underlying time appear to be six hours apart depending on where you look.

**Fix:**

1. Detect whether the parsed source carried timezone information. Record it on the row as
   `timeHadOffset` (boolean) during the timestamp parsing block.
2. When it did not, the app is guessing. **Make the guess explicit rather than silent:** parse
   offset-less timestamps as **UTC**, not local. UTC is the right default for EDR data, matches
   what the charts already do, and makes the table and charts agree by construction.
3. Show the assumption once, in the post-analysis toast: `· timestamps without a timezone read as
   UTC`. Only when at least one such row exists.
4. Add `UTC` to the Time column header so the reader knows what they are looking at.

**Do not** convert the table to local time to match — that would make the charts wrong instead, and
UTC is correct for this data.

**Tests:** unit tests on the parsing helper for an offset-bearing string, an offset-less string, a
10-digit epoch and a 13-digit epoch. Then a Playwright assertion that a known fixture row renders
the same hour in the table as on the chart axis.

## 4. Task C — Axis labels are unreadable at realistic spans

**Where:** `getAutoBucketInterval()` in `src/auditor/buckets.js`; chart `scales.x.ticks` options.

Current thresholds:

```
≤ 1 hour  → 1 min
≤ 6 hours → 5 min
≤ 3 days  → 1 hour
> 3 days  → 1 day
```

A 5½-hour capture — a realistic working dataset — falls in the second band and produces roughly
**66 buckets** on a canvas about 450 px wide, rendered as 45°-rotated labels that overlap into
illegibility. The screenshots show this clearly.

The thresholds are not wrong in isolation; they are wrong because **they ignore how wide the chart
actually is.** Two charts sit side by side, so each gets half the container.

**Fix — do both parts:**

1. **Cap the tick count, not the bucket count.** Keep bucketing as-is (the data resolution is
   fine); limit rendered labels via Chart.js `ticks.maxTicksLimit`, set from the canvas width —
   roughly one label per 60–80 px. Chart.js will thin them evenly. Do **not** reduce the number of
   data points; the line shape is the value.
2. **Add a bucket count to the auto option label.** The dropdown currently reads `Auto`. Make it
   read `Auto (5 min)` once data is loaded, so the user can see what was chosen and override
   knowingly.

Leave the four thresholds themselves unchanged unless the screenshots after step 1 still look
crowded.

**Test:** a Playwright assertion that with the 5½-hour fixture loaded, the number of rendered x-axis
tick labels on the Requests chart is below 20.

## 5. Task D — Single-bucket and empty states

**Where:** `renderGapCharts()`, `renderSingleChart()`.

When all records fall in one bucket — a short capture, or a narrow filter — line charts render an
axis with a single point and no line. Four of five charts then look broken. This is the default
experience for anyone uploading a small sample, and it reads as "the tool is broken" rather than
"there is not enough data to plot".

**Fix:** when a chart resolves to fewer than two buckets, do not render an empty axis. Replace the
canvas with a short message inside the same card:

> All 20 records fall within one 5-minute bucket. Choose a finer bucket size to see a trend.

Include the actual record count and the actual interval. The bucket dropdown stays visible and
usable, directly above the message.

Apply the same treatment when a filter reduces a chart to zero rows: *No records match the current
filter.*

**Test:** upload a fixture spanning under a minute and assert the message element is present and the
canvas is not rendered.

## 7. Task F — Encoding changes — REQUIRES SIGN-OFF, DO NOT IMPLEMENT UNTIL APPROVED

Two charts use an encoding that does not suit their data. Both changes alter what the chart *means*,
so they are product decisions.

**Present both to Sanjoy with the reasoning below and wait.**

### F1. Requests Over Time draws two nearly identical lines

With balanced data — 192 signing, 192 verification — the two series coincide almost exactly and the
blue line is hidden beneath the green except where they diverge. The chart spends its whole area
showing that the two numbers are the same, and renders the one interesting feature, divergence, as
a barely visible sliver.

**Proposed:** keep the two lines, and shade the area between them. Where they coincide the shading
vanishes; where they diverge it is immediately visible and proportional to the gap. No information
is lost and the signal becomes the most prominent thing on the chart.

**Alternative if that is too subtle:** plot a single request-volume line plus a separate signed
divergence series on a second axis.

### F2. Invalid Numbers Over Time is 95% flat zero

Seven invalid destinations across 5½ hours renders as a flat line at zero with four spikes. A
continuous line implies a rate; these are discrete, rare events.

**Proposed:** switch to a scatter or lollipop encoding — one mark per event, at its actual
timestamp, no interpolation between them. Rare events read correctly as events, and clicking a mark
can still drill through to the record.

**Counter-argument worth weighing:** if invalid numbers ever arrive in volume, a line chart is the
better encoding and switching back would be another change. Ask Sanjoy whether seven-in-5½-hours is
typical of his data or an artefact of a clean sample.

## 10. How this project has failed before

You do not have access to the project's memory document. These three patterns have each recurred
across several phases. Read them before starting.

**Tests that assert nothing.** Six Playwright tests once re-implemented application logic inside
`page.evaluate()` and asserted against their own copy — including a physics test that computed a
value and discarded it, while the suite reported "182 passing". A later file asserted
`expect(40 + 60).toBe(100)`. **A test that cannot fail is worse than no test**, because it stops
anyone looking. The check takes seconds: delete the thing the test names, run it, confirm it goes
red.

**A claimed blocker is a claim like any other.** The Phase 3 report skipped screenshots because the
capture tooling "was deleted in Phase 2". It had not been — it was untracked and moved, and sat in
the working folder the whole time. **Treat "I couldn't because X" exactly as you treat "it works":
verify X before reporting it.**

**Fixes land one condition too narrow, or relocate the bug.** A toast merge missed a third call in
the same function. A country-code fix removed a wrong value from a label and reintroduced the
identical defect in the tooltip, with unit tests then certifying it correct. **When closing an item,
read the whole function, and ask where else the thing you just fixed now lives.** For this phase
that means: colours are defined in both `renderGapCharts()` and `renderSingleChart()`. Fix both.

**If any statement in this document turns out to be wrong when checked against the code, say so and
stop** rather than working around it.
