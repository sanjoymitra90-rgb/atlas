## 1. The requirement

**Every time the application displays or plots is UTC. There are no exceptions and no viewer-local
rendering anywhere.**

This is a product decision from the maintainer, not an implementation preference. The tool is used
to reconstruct what happened during an incident, often days later, frequently by more than one
person. A timestamp that means something different depending on who opened the file is worse than
no timestamp, because it looks authoritative while being wrong.

Two people opening the same CSV in different countries must see identical times, and those times
must match what the source system recorded.

---

## 2. The bug this fixes

An ISO timestamp with **no offset** — `2026-01-15T10:30:00` — is currently parsed by `new Date()`,
which the JavaScript specification says to interpret as **the reader's local time**.

The source data is UTC. So on a machine set to UTC+6:

```
source row:      2026-01-15T10:30:00      (which is 10:30 UTC)
parsed as:       2026-01-15T04:30:00Z     (10:30 local, converted)
table shows:     10:30                    (raw string — correct)
chart buckets:   04:30                    (six hours from reality)
```

**The charts plot real events at the wrong hour, and the table beside them tells the truth.** The
error equals the viewer's UTC offset.

**This is invisible in CI**, which runs UTC — everything agrees there. It only appears on a
developer's or user's machine. That is why no test has ever caught it.

Verified by executing `parseGapTimestamp` under two timezones: `TZ=UTC` yields `1768473000000`;
`TZ=Asia/Dhaka` yields `1768451400000`. Same code, same input, six hours apart.

---

## 3. The rule to implement

**The Time column always shows UTC.**

| Source value | Display | Converted? |
|---|---|---|
| `2026-01-15T10:30:00Z` | `10:30` | no — already UTC |
| `2026-01-15T10:30:00` (no offset) | `10:30` | no — assumed UTC |
| `15/01/2026 10:30` | `10:30` | no — assumed UTC |
| `2026-01-15T10:30:00+05:30` | `05:00` | **yes** |
| `1706140800` / `1706140800000` (epoch) | readable UTC date-time | **yes** |

The maintainer's current data lands entirely in the "no conversion" rows, **so the table must look
identical to today for that data.** If your change alters the displayed text for an offset-less or
`Z`-suffixed row, you have gone too far — stop and report.

## 5. Task A — Parse offset-less input as UTC

### A1. The change

In `parseGapTimestamp()` in `src/auditor/time.js`, an input carrying no timezone offset must be
interpreted as UTC rather than as local time.

The epoch branches and the `D/M/YYYY` branch are already correct — epochs are absolute and the
`D/M/YYYY` branch already uses `Date.UTC`. **Do not touch them.** Only the final `new Date()`
fallback is wrong.

### A2. The trap — read this before you write the fix

**Do not simply append `Z` to the string.** The fallback branch currently accepts formats that are
not ISO, and appending `Z` breaks them. The clearest example is in `fixtures/gap-xss-time.csv`,
whose first row begins `Jan 1 2025 (...)` — that parses today, and `new Date('Jan 1 2025Z')` does
not.

Handle the ISO-shaped case explicitly and leave other formats reaching `new Date()` as they do now.
Widening the fix to every possible format is out of scope; **narrowing behaviour that currently
works is a regression.**

### A3. Prove you have not broken anything

Before and after your change, run `parseGapTimestamp` against a table of inputs and print
`{ timestamp, timeValid, timeHadOffset }` plus the UTC rendering. Include at minimum:

- `2026-01-15T10:30:00Z`
- `2026-01-15T10:30:00+05:30`
- `2026-01-15T10:30:00` ← the one that must change
- `2026-01-15 10:30:00` (space instead of `T`, no offset)
- `15/01/2026 10:30`
- `1706140800` and `1706140800000`
- `Jan 1 2025 (<img src=x onerror=alert(1)>)` ← must still parse, exactly as before
- `not-a-date` and empty

**Exactly one row should change.** Put the before/after table in your hand-back. If more than one
row changed, you have caught a second bug or caused one — either way, stop and report.

### A4. Prove it under two timezones

Run the same table with `TZ=UTC` and with `TZ=Asia/Dhaka`. **After the fix, every value must be
identical between the two runs.** Before the fix, the offset-less row differs. Include both runs in
your hand-back.

This is the single most important verification in this phase.

## 6. Task B — The Time cell shows UTC

### B1. Where

`renderGapTable()` builds the Time cell in **two branches** — grouped and flat — and they are
currently identical. **Both must change.** Fixes applied to only one of these two branches have
shipped before in this project.

The cell currently prints `row.time`, the raw source string, under a header reading "Time (UTC)".

### B2. What to render

Render from the parsed timestamp, formatted as UTC, in a stable readable form. For every source
format the maintainer currently uses, this must produce **the same visible text as today** — a
`Z`-suffixed or offset-less ISO string already displays its UTC clock time.

The rows whose display changes are exactly the two in §3 marked *converted*: offset-bearing
timestamps, and epochs, which currently render as a raw unreadable number.

Rows with `timeValid === false` keep their current behaviour — the amber icon and the raw text,
unchanged. There is no timestamp to render, and the user needs to see what could not be parsed.

### B3. Keep the original where it differs

**When the rendered value differs from the source string, put the source in the cell's `title`
attribute** — `source: 2026-01-15T10:30:00+05:30`.

Two reasons, both real. Someone cross-referencing a provider's log needs the value that provider
will quote back at them. And it makes the conversion auditable rather than something a user has to
take on trust the first time a shifted time looks wrong to them.

Where the value is unchanged, do not add a tooltip — a tooltip that says the same thing as the cell
is noise.

**Escape it.** This is user-supplied CSV content entering an HTML attribute, and this project has
shipped an XSS through exactly that path before.

## 7. Task C — Export carries both

`exportGapData()` writes `row.time` — the raw source string — for the Time column.

Once the application displays UTC, an export that disagrees with the screen is a defect. **Export
the UTC value**, and **keep the original as a second column** rather than replacing it.

Anyone with a downstream script is currently parsing the raw value; silently changing what that
column contains would break them without a signal. A new column beside it does not.

Name the new column so its meaning is obvious without documentation. Apply the change to the
detail-row export only — the pair-summary branch has its own time columns and is out of scope
unless you find it inconsistent, in which case report rather than fix.

## 8. Task D — Make the tests capable of catching this

### D1. A fixture that exercises conversion

No fixture contains an offset-bearing timestamp, which is why the A5 cross-check test passes while
the bug exists. Add to `fixtures/gap-screenshots.csv`, or a new fixture if that one is at capacity:

- at least one row with an explicit non-UTC offset, e.g. `+05:30`
- at least one offset-less row
- at least one epoch row

Keep the pairing behaviour of that fixture intact — it currently produces about 30 pairs and the
screenshot harness and theme test both depend on that. **Confirm `pairedPairs` after your change**
rather than assuming.

### D2. Extend the cross-check test

The A5 test in `e2e/gap/gap-charts.spec.cjs` compares the table hour with the chart axis hour. Extend
it to assert this for **an offset-bearing row specifically** — that is the case that would have
caught this.

### D3. The timezone-independence test

Add a unit test that fails if parsing is timezone-dependent. The mechanism is yours to choose, but
it must actually exercise a non-UTC timezone — asserting a hardcoded number in a UTC-only runner
proves nothing.

**If you cannot make this genuinely timezone-varying within the existing setup, say so plainly and
describe what you tried.** An honest "not achievable without X" is worth more than a test that
appears to cover this and does not. This project has shipped several of the latter.
