## 1. What Phase 3 is

Three tasks. The first is the substance; the other two are small.

- **A — the reason vocabulary.** Make the Destination Issues chips say what is actually wrong, at
  the granularity an Ops person needs, and make that impossible to drift again.
- **B — the Attention panel.** Move the breakdown to where it is useful: directly above the table
  it filters.
- **C — Call Pairing layout.** Close the hole in the grid. Nothing else about that panel changes.

**What Phase 3 is not.** An earlier plan had the four pairing outcome blocks moving out of Call
Pairing and into a combined Attention panel. **That was reconsidered and rejected**, because the
pairing panel is global and the destination chips are filter-responsive — putting both in one panel
means clicking a chip changes half the numbers and freezes the other half. The outcome blocks stay
exactly where they are.

## 3. Task A — the reason vocabulary

### A0. The problem

Under the tiles, when a file contains bad destination numbers, a panel headed "Destination Issues —
breakdown" renders a row of clickable chips. Clicking one filters the table to those rows. The
chips currently read as raw internal slugs — `malformed ×7`, `suspected-test ×2` — because the
display-label map in `renderGapMetrics()` still holds a vocabulary that the categorisation code
stopped producing several phases ago. Only `empty` and `other` still line up.

There are two faults here, and the second one matters more.

**Fault one: the labels are stale.** Easy to fix.

**Fault two: category identity is derived by substring-matching English prose.**
`gapReasonBucket()` decides a number is malformed by testing whether its human-readable reason
string contains `length`, or `prefix`, or `+44`. The reason strings are user-facing copy.
**Phase 5 is a copy sweep.** The first time someone rewords "Invalid length", the chips break
silently and nothing fails. Fixing only the labels leaves that trap armed.

### A1. Make the bucket a returned value, not an inference

`validateUKNumber()` in `src/auditor/validate.js` already returns `valid`, `category`, `reason`
and — since the last fix — `countryCode`. **Add a `bucket` field**, set explicitly at each return
point. The function already knows exactly why it rejected a number; stop making a second function
guess from the prose.

Then:

- **Carry it onto the row** where the gap row is built, as `ukBucket` — the same way
  `ukCountryCode` is carried.
- **Update the two consumers** to read `row.ukBucket` directly: the filter predicate in
  `applyGapFilters()`, and the `reasonCounts` tally in `exportGapData()`.
- **Delete `gapReasonBucket()`** and its `describe` block in `src/auditor/validate.test.js`.
  Replace those with assertions on the `bucket` field returned by `validateUKNumber()` — one case
  per bucket, driven by real phone numbers rather than by reason strings.

After this, no code anywhere decides a category by reading prose.

### A2. The seven buckets

| `validateUKNumber` rejects because | `bucket` | chip label |
|---|---|---|
| the value is empty | `empty` | Empty |
| the number is valid but not British | `non-uk` | Non-UK |
| it does not begin `+44` | `not-plus-44` | Not +44 |
| it has too few or too many digits | `wrong-length` | Wrong length |
| the digit after `44` is not 1, 2, 3, 7 or 8 | `bad-prefix` | Bad prefix | 
| every digit is the same | `identical-digits` | Identical digits |
| five or more digits run consecutively | `sequential-run` | Sequential run |
| — anything unforeseen — | `other` | Other |

`other` is a safety net and should never appear in practice. If it shows up while you are testing,
something is wrong — report it rather than papering over it.

**Bucket names are internal identifiers and must never be shown to a user.** That is the mistake
being fixed.

### A3. Labels live next to the buckets

Export a label map from `src/auditor/validate.js`, immediately beside the bucket definitions, and
import it where the chips render. **The two must sit in the same file**, so that adding a bucket
without a label is visible in the diff. The current split — buckets in one module, labels in a
local `const` buried in a rendering function in `index.html` — is precisely how they drifted apart.

Sentence case, as in the table above. Chips read `Wrong length ×7`.

### A4. Two different granularities — do not merge them

There are now two distinct classifications and they are not the same:

- **`category`** — coarse. Drives the pill in the table's UK Valid column and its colour:
  `valid`, `malformed`, `non-uk`, `suspected-test`. **Unchanged by this phase**, except for the
  deletion in A5. A compact badge in a dense table is the right place for four values.
- **`bucket`** — fine. Drives the breakdown chips and the table filter. Seven values.

Do not collapse them into one field, and do not make the table pill fine-grained.

### A5. Delete the `truncated` category

Nothing produces it. `gapReasonBucket()` and `ukPillHtml()` both handle it, and it has been carried
dead through several phases. Remove it from both, from the label and style maps in `ukPillHtml()`,
and delete the `gapReasonBucket('Truncated value')` assertion when you delete that test block.

If you find anything that *does* produce it, stop and report — that would contradict this
document.

### A6. The chips have no test coverage at all

Nothing in `e2e/` references `.gap-reason-chips` or `#gap-invalid-reason-panel`. That is why this
drifted for several phases without a single failure.

Add a Playwright test using `fixtures/gap-invalid-only.csv` that asserts:

- the panel becomes visible when a file contains invalid destinations
- **no chip's text contains a bucket identifier** — assert against the internal names directly, so
  this exact regression cannot recur
- clicking a chip filters the table, and the visible row count matches the chip's count
- clicking the same chip again clears the filter

Check whether `gap-invalid-only.csv` covers enough buckets. If it does not, extend it or add a
fixture — and say which you did.

## 8. Notes for the implementing agent

- **Run the function, don't read it.** The modules under `src/` are plain ES modules with no DOM
  dependency and run under bare `node` — no test runner, no install step. Write a scratch file,
  import `validateUKNumber`, and print a table of number → `{category, bucket, reason,
  countryCode}` for every case in A2. Do this before you write the rendering code, and again after.
  This technique has found more defects in this project than any other.
- **Check that a selector exists before you write a test against it.** Four tests in the last phase
  were written against an export modal that does not exist, and three of them targeted the wrong
  module. One grep each would have caught all four.
- **`escapeHtml()` the chip labels.** They are static strings today, but the chips are built by
  string concatenation into `innerHTML`, and the counts come from data.
- **Two things named "reason" are not the same thing.** `row.ukValidationReason` is prose for the
  tooltip. `row.ukBucket` is an identifier for logic. Keep them apart.
