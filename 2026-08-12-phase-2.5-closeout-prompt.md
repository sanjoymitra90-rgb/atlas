## 3. Task J — fix the four broken tests

All four are in `e2e/gap/gap-review.spec.cjs`. They share one root cause and three of them are in
the wrong module.

### The root cause

The gap export modal (`#gap-export-modal`) contains **three** buttons, wired to
`confirmGapExport('filtered')`, `confirmGapExport('all')` and `confirmGapExport('pairs')`. Their
visible labels are "Filtered Results", "All Results" and "Pair Summary".

**There is no button whose text contains "CSV" or "JSON".** The format is always CSV; the choice is
about scope. `confirmGapExport()` sets `window.gapExportAllData` / `window.gapExportPairs`, then
calls `exportGapData()` on a short timeout.

Three of the four tests look for buttons that do not exist. Because every interaction is wrapped in
`if (await x.isVisible({ timeout: 2000 }).catch(() => false))`, the missing element is swallowed
and the test continues, failing much later at a download timeout or a count assertion instead of at
the point where the assumption broke.

### J0. Remove every `if (await …isVisible().catch(() => false))` guard — do this first

Across all four tests. If an element is required for the test to mean anything, its absence must
fail the test immediately and loudly. These guards are the reason four broken tests looked
plausible enough to commit.

### J1. There is already a working export pattern in this repo — use it

`e2e/gap/gap-dup.spec.cjs`, the test named *"export CSV includes duplicate in pairing summary"*,
passes today and exports without touching the UI:

```js
const download = page.waitForEvent('download');
await page.evaluate(() => {
  window.gapExportAllData = true;
  window.exportGapData();
});
const dl = await download;
const content = require('fs').readFileSync(await dl.path(), 'utf8');
```

Copy this shape for B3, B5 and B6. Driving the export through the window bridge is more robust than
clicking through a modal, and it is the established convention in this suite.

### J2. B3 — CSV header with a comma in a custom column name

Currently fails on a download timeout, because it clicks a "CSV" button that does not exist.

**Two problems, fix both:**

- **It never exports.** Replace the modal-clicking with the J1 pattern.
- **Its assertion cannot fail.** `expect(commaCount).toBeGreaterThanOrEqual(9)` passes on the
  default header, which has twelve columns and eleven commas, whether or not a custom column was
  ever added. Assert the **exact** expected column count with the comma-named column present.

For the custom column itself, the reliable route is to set `gapAdditionalColumns` directly inside
`page.evaluate` before exporting. The UI route, if you prefer it: the `+ Add Column` button calls
`addGapAdditionalColumn()`, rows render into `#gap-additional-columns`, and the mapping is applied
by `confirmGapColumnMapping()` (testid `gap-analyze-btn`).

**Prove it fails:** revert `csvCell` on the header row in `exportGapData()` — the header becomes
`allHeaders.join(',')` — and confirm the test goes red.

### J3. B5 — blob URL revocation

Currently fails at `expect(counts.create).toBeGreaterThan(0)`, because it clicks a "JSON" button in
the gap analyzer. **The gap analyzer has no JSON export.** JSON export is `exportSessionJSON()`,
which belongs to the optimizer and uses a `data:` URI, not a blob — so it would not have exercised
this fix even if it had been reachable.

**Fix:** use the gap CSV export via the J1 pattern. All three blob export sites go through the
single `downloadBlob()` helper in `src/core/download.js`, so exercising one path genuinely covers
the fix.

Keep the existing stub-and-count approach — it is sound. Assert both that `create > 0` and that
`revoke >= create`.

If you want coverage of all three blob sites, add `exportShareReport()` in the optimizer spec as a
second test. Optional.

**Prove it fails:** remove the `URL.revokeObjectURL(url)` line from `downloadBlob()` and confirm
the test goes red.

### J4. B6 — Gap column absent from the export summary

Same root cause as B3: no "CSV" button, download times out. Same fix — use the J1 pattern.

The assertions themselves are fine and should be kept.

**Prove it fails:** add a `Gap` column back into the summary header in `exportGapData()` and
confirm the test goes red.

### J5. B2 — scenario name XSS — move this to the optimizer

This test is in the wrong module twice over. It writes to `localStorage['gapScenarios']`; the app
uses **`atlas-opt-scenarios`**. It then opens `#gap-column-modal`, the gap analyzer's settings
modal, looking for a scenario list that is rendered by `renderScenarioList()` into `#scenario-list`
inside `#scenarios-modal` (testid `scenarios-modal`), opened by `openScenariosModal()` — all of
which belong to the **optimizer**, not the gap analyzer.

**Fix:**

- Move the test to `e2e/optimizer/opt-review.spec.cjs`, where the module it tests actually lives.
  Delete it from `gap-review.spec.cjs`.
- Seed `atlas-opt-scenarios` with a scenario carrying the payload as its `name`. Read
  `getOptScenarios()` and `saveOptScenario()` to get the stored object shape right —
  `renderScenarioList()` reads `name`, `ts` and `summary`.
- Open the modal via `openScenariosModal()`.
- Assert `#scenario-list` contains no element node matching the payload, **and** that its
  `textContent` includes the literal payload string.

**Prove it fails:** remove the `escapeHtml()` wrapper from `s.name` in `renderScenarioList()` and
confirm the test goes red.

## 6. Why constraint 2 exists — read this before you write a test

This project has shipped tests that report coverage they do not have in **three consecutive
phases**:

- **Before Phase 1** — six Playwright tests re-implemented application logic inside
  `page.evaluate()` and asserted against their own copy. The physics test computed the
  light-in-fibre floor and then discarded it. The suite was reported as "182 passing".
- **Phase 2** — `src/auditor/pairing.test.js` asserted `expect(40 + 60).toBe(100)` and checked a
  property on an object it had constructed two lines earlier. It imported nothing from the
  application and would have passed if `pairGapCalls()` were deleted.
- **Phase 2.5** — four tests written against a UI that does not exist, three of them aimed at the
  wrong module entirely.

Each time, the tests looked plausible and were committed with a message describing coverage that
was not there. Each time, the next person had to discover it.

**One check catches all three, and it takes seconds: delete the thing the test names, run the test,
and confirm it goes red.** None of these would have survived it.

Do this for every test you touch, and say so in the commit message.
