## Task A — Column filter dropdowns trigger the column sort

**Reported behaviour:** open the filter beside "UK Valid", click the dropdown without choosing
anything different, and the table changes. Click again and it changes back. Nothing is filtered —
the rows are being re-sorted.

**Cause, verified.** The `.gap-col-dropdown` div is a **child of the `<th>`**, and the `<th>` carries
`onclick="handleGapSort('…')"`. Only the filter icon span calls `event.stopPropagation()`. Every
other click inside the dropdown — the `<label>`, the `<select>`, the surrounding padding — bubbles
up to the `<th>` and fires the sort. A second click toggles `gapSortAscending`, which is why it
appears to flip back and forth.

The dropdown is `position: fixed`, so it renders visually outside the header — but it is still a DOM
descendant, and events bubble through the DOM tree, not the visual one.

**Fix — preferred:** stop the propagation at the dropdown container. Every `.gap-col-dropdown`
element gets `onclick="event.stopPropagation()"`. Apply it to all of them, not just `ukCategory` —
the same defect exists on every column.

**Fix — better, if the refactor is small enough to be safe:** the dropdowns are `position: fixed` and
positioned by script already, so nothing requires them to live inside the `<th>`. Move them to a
single container at the end of `<body>`. That removes the bubbling relationship entirely rather than
suppressing it. Take this route only if it can be done without disturbing `toggleColFilter()`,
`repositionOpenColDropdowns()` and `closeAllColDropdowns()`; otherwise take the preferred fix and
note the structural option in the commit message.

**Tests — both required:**

1. For each column filter: open the dropdown, click the control without changing its value, and
   assert the first row of the table is unchanged.
2. For each column filter: open the dropdown, click the control, and assert `gapSortColumn` and
   `gapSortAscending` are unchanged.

The second is the one that would have caught this.

## Task A2 — Group-by-pair: the first pair on each page has no summary row

**Also a live bug. Do it alongside Task A.**

**Reported behaviour:** with Group by pair enabled, every paired group shows its
`P{n} · handoff … · proc … · end-to-end …` summary row except the first one.

**Cause, verified.** In `renderGapTable()`, the grouped branch computes one flag and uses it for two
unrelated purposes:

```js
const isFirst = rowIsFirstInGroup[row._gapIdx] && gi > 0;

if (isFirst) trClasses += ' gap-group-seam';                 // needs gi > 0
if (isFirst && isPairGroup && row.pairId) { … summaryRow … } // must NOT need gi > 0
```

The `&& gi > 0` is correct for the **seam** — no divider above the first group on a page. It is
wrong for the **summary row**, which belongs to every paired group.

Note that `gi` is the group index *within the current page*, so this suppresses the summary row on
the first group of **every page**, not only the first page. Any test must therefore check a page
other than the first as well.

**Fix:** separate the two concerns.

```js
const isGroupStart = rowIsFirstInGroup[row._gapIdx];
const needsSeam = isGroupStart && gi > 0;
```

Use `needsSeam` for the `gap-group-seam` class and `isGroupStart` for the summary row.

**Test:** with Group by pair on and a fixture containing several pairs, assert the number of
`.gap-pair-summary` rows equals the number of paired groups on the page. Repeat on page 2. Asserting
only "a summary row exists" would pass today.

**While here:** this is a conflated-flag bug. Check whether `isAlt` (the zebra banding) has the same
problem — it derives from `gi` too.

## Task B — Revert the pairing-key remove button to a floating badge

**Phase 4.5 Task D1 was a regression and should be undone.**

The remove control was moved from a floating badge into the row's normal flow. The badge position
was deliberate: the pairing key renders as `From × + To ×`, and an inline `×` reads as a
multiplication sign next to the `+` separator rather than as a delete control. Moving it in-flow
makes the row ambiguous.

**Restore the floating badge.** Then fix the actual defect that was reported — the badges rendering
on top of the "Map CSV Columns" title when the modal body is scrolled.

That is a stacking and clipping problem, not a placement problem:

- The badges carry `z-10`; the modal header does not establish a higher stacking context
- The scrollable modal body does not clip its overflowing children

**Fix:** give the modal header a `z-index` above the badges and its own stacking context, and ensure
the scrolling region clips overflow so absolutely-positioned children scroll with their content
rather than over the header. Verify by scrolling the mapping modal with three or more pairing key
components added.

**Keep the visual softening if it was part of D1** — a muted glyph that brightens on hover is better
than a bright red filled circle. Change the styling, keep the position.

## Task D — Empty states, fixtures, and axis ticks

### D1. Time to Verify renders an empty axis instead of a message

Visible in `screenshots/11-charts-populated.png`: TTV shows a bare 0.0–1.0 grid with no data and no
message. The fixture produces no pairs, so there is nothing to plot — but `showChartMessage()` does
not fire for this case.

The empty-state guard evidently keys on bucket count, not on whether the series has any data. A
chart with zero data points must show the message, not an empty axis. **This applies to all three
timing charts** once Task C lands, since all of them are empty when there are no pairs.

Suggested message: *No paired calls in the current view.*

### D2. The populated fixture cannot demonstrate the charts

`fixtures/` gained a populated fixture in Phase 4.5, but it has roughly one record per bucket, no
pairs, and never both a valid and an invalid record in the same bucket. Consequences:

- The volume chart's stacking is invisible — the whole point of that chart
- All three timing charts are empty
- The y-axis runs 0.0–1.0 with decimal ticks

**Rebuild it** to span several hours with, per bucket, multiple records, a mix of valid and invalid
destinations, and genuine signing/verification pairs with varied handoff and processing times. It
should look like a plausible working day. This fixture is the only way anyone can see whether the
charts work.

### D3. Count axes should use integer ticks

Requests Over Time and Signing vs Verification Volume plot counts. Set
`ticks: { precision: 0 }` on their y-axes so the scale reads 0, 1, 2 rather than 0.0, 0.2, 0.4.
Leave the timing charts alone — milliseconds are legitimately fractional.

## Task F — Make it impossible to test a stale build

Phase 4's suite was reported green locally and failed immediately in CI on a deterministic
assertion. The mechanism: Playwright runs against `dist/index.html`, but only `npm test` rebuilds
first. Four other scripts run against whatever build is on disk.

### F1. Every e2e script builds first

```json
"test:e2e":       "npm run build && playwright test",
"test:gap":       "npm run build && playwright test --project=gap",
"test:optimizer": "npm run build && playwright test --project=optimizer",
"test:headed":    "npm run build && playwright test --headed",
"test":           "npm run test:unit && npm run test:e2e"
```

The last line prevents the double build that would otherwise result. Confirm `npm test` still runs
units, then one build, then the full suite.

### F2. A staleness guard that fires regardless of how tests start

F1 is not sufficient — `npx playwright test`, an IDE runner or a hand-written CI step all bypass npm.

In `e2e/global-setup.js`, before the existing CDN check:

1. Fail if `dist/index.html` is missing.
2. Fail if `dist/index.html` is older than the newest of `index.html` and everything under
   `src/**/*.{js,css}`. A change to `src/auditor/validate.js` invalidates the build just as surely,
   and unit tests import `src/` directly so they would not catch it.

Compare `mtimeMs`. Throw from `globalSetup` so the run aborts before any test executes. No new
dependencies — a recursive readdir and a max is enough.

### F3. Prove the guard fires

Touch `index.html` without changing its content, run `npx playwright test` directly, and confirm the
run aborts with the stale-build message before any test runs. Then build and confirm it proceeds.
**State in the commit message that you did this and what you saw.**

### F4. Explain it in DEPLOY.md

Two or three sentences, in the plain register of that file: the tests run against the built copy, not
the source; every test command now rebuilds automatically; if something bypasses that, the tests
refuse to run rather than checking an old version.

## How this project has failed before

You do not have access to the project's memory document. These patterns have each recurred.

**Tests that assert nothing, and suites reported green without being run.** Six Playwright tests
once asserted against their own re-implementation of the code while the suite reported "182
passing"; a later file asserted `expect(40 + 60).toBe(100)`; Phase 4 reported all-green with a
different test failing in CI. **Run the full suite and paste the real output.**

**Guards that swallow missing elements.** `if (charts) charts.scrollIntoView(...)` produced two
phases of wrong screenshots. Four tests hid missing elements behind
`isVisible().catch(() => false)`. **A missing element is a failure, not a branch.** Task E2 is
exactly this.

**Fixes land one condition too narrow, or relocate the bug.** A toast merge missed a third call in
the same function; a country-code fix moved its own defect into the tooltip. Task A is a live
example: the filter icon stops propagation, but nothing else in the dropdown does. **Fix the class,
not the instance** — apply it to every column, not the one that was reported.

**Changing something without knowing why it was that way.** Phase 4.5 moved the pairing-key remove
button in-flow to fix an overlap. Its floating position was deliberate — inline, the `×` reads as a
multiplication sign beside the `+` separator. The overlap was real; the chosen fix was not.
**When a piece of UI looks odd, ask why it is that way before changing it.**

**If any statement in this document turns out to be wrong when checked against the code, say so and
stop.**
