# ATLAS — Phase 4.6: Make it impossible to test a stale build

**For:** the AI coding agent.
**From:** review, 2026-08-13.
**Run after Phase 4.5 lands.** Small, single-purpose, one or two commits.

**No line numbers in this document.** Anchor on file names and script names.

---

## Why this exists

Phase 4's suite was reported green locally and failed immediately in CI, on a deterministic
assertion — the TTV canvas being hidden, thirteen consecutive resolutions, failing again on retry.
Nothing about it was flaky.

The mechanism: since Phase 1, Playwright runs against **`dist/index.html`**, the built file. Only
`npm test` rebuilds first. Four other scripts run Playwright directly against whatever build happens
to be on disk:

```
test        →  test:unit && build && test:e2e     ← builds
test:e2e    →  playwright test                    ← does not build
test:gap    →  playwright test --project=gap      ← does not build
test:optimizer →  playwright test --project=…     ← does not build
test:headed →  playwright test --headed           ← does not build
```

So editing `index.html` and then running `npm run test:gap` tests the **previous** build. Phase 4's
change hides the TTV canvas; the stale build still showed it; the test passed. CI built fresh and
the test failed.

**The bug is not that someone ran the wrong script. The bug is that running the wrong script is
possible and silent.** Correctness currently depends on remembering which of five commands rebuilds,
and nothing tells you when you have got it wrong.

---

## Task A — Every e2e script builds first

In `package.json`:

```json
"test:e2e":       "npm run build && playwright test",
"test:gap":       "npm run build && playwright test --project=gap",
"test:optimizer": "npm run build && playwright test --project=optimizer",
"test:headed":    "npm run build && playwright test --headed"
```

**Then fix the resulting double build.** `test` currently reads
`test:unit && build && test:e2e`; with the above, it would build twice. Change it to:

```json
"test": "npm run test:unit && npm run test:e2e"
```

Confirm `npm test` still runs units, then a build, then the full Playwright suite, in that order.

---

## Task B — A staleness guard that fires regardless of how tests are started

Task A is not sufficient. Playwright can be launched directly — `npx playwright test`, an IDE
runner, a VS Code extension, a CI step written by hand — and all of those bypass npm scripts
entirely.

**Add the check to `e2e/global-setup.js`**, which already runs before every suite and already
performs the CDN dependency check. Before that check:

1. Fail if `dist/index.html` does not exist:
   `dist/index.html not found — run npm run build first.`
2. Fail if `dist/index.html` is older than `index.html`:
   `dist/index.html is older than index.html — the build is stale. Run npm run build.`

Compare `fs.statSync(...).mtimeMs` for both. Throwing from `globalSetup` aborts the run before any
test executes, which is the behaviour we want — a stale run should not start, not fail confusingly
in the middle.

**Also compare against `src/`.** A change to `src/auditor/validate.js` invalidates the build just as
surely as a change to `index.html`, and unit tests import `src/` directly so they would not catch
it. Take the newest mtime across `index.html` and everything under `src/**/*.js` and `src/**/*.css`,
and compare that against `dist/index.html`.

Keep it simple — a recursive readdir and a max over mtimes. Do not add a dependency for this.

---

## Task C — Prove the guard works

Consistent with the discipline this project now applies to every safety mechanism: **a guard that
has not been seen to fire is not a guard.**

1. Touch `index.html` without changing its content (`fs.utimesSync`, or just save it).
2. Run `npx playwright test` directly, bypassing npm.
3. Confirm the run **aborts before any test executes**, with the stale-build message.
4. Run `npm run build`, run the suite again, confirm it proceeds normally.

**State in the commit message that you performed this and what you saw.**

---

## Task D — Document it for the maintainer

Add a short section to `DEPLOY.md`, in the same plain-English register as the rest of that file:

> **Why the tests sometimes rebuild first.** The tests run against the built copy of the app, not
> the source. If the build is older than your changes, the tests would be checking the old version.
> Every test command now rebuilds automatically, and if something bypasses that, the tests refuse to
> run and tell you to build first.

Two or three sentences. The audience is a non-developer who needs to understand why a test command
sometimes takes an extra thirty seconds.

## Definition of done

- [ ] All four e2e scripts build before running Playwright
- [ ] `npm test` builds exactly once
- [ ] `globalSetup` aborts when `dist/index.html` is missing, or older than the newest file in
      `index.html` or `src/`
- [ ] The guard was made to fire on purpose, bypassing npm, and this is stated in the commit message
- [ ] `DEPLOY.md` explains the behaviour in plain English
- [ ] CI still passes end to end

## Note on the failure mode this closes

This project has repeatedly produced confident results from tooling that was measuring the wrong
thing: a physics test that computed a value and discarded it; a screenshot harness pointed at the
unbuilt source for two phases; a chart capture scrolling to a selector that matched nothing, behind
a guard that swallowed the miss.

Each time, something ran, produced a plausible artefact, and reported success. This one belongs to
the same family — a test suite that passes because it is examining yesterday's build.

**The general fix is the same each time: make the wrong thing loud instead of silent.** That is what
Task B is for, and it is why Task C is not optional.
