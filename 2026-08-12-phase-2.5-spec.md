because the audit found three categories of leftover that should not be carried into Phase 3:

## 3. Task G — Import and onboarding correctness

Six bugs. All are in code Phase 2 touched. Each is its own commit, test first.

### G1. The dropped-items count is doubled

**Where:** `handleImport()`.

The lat/lng validation filter increments `droppedEndpoints` inside the predicate, and then the
same drops are added a second time from the length difference:

```js
customers = customers.filter(c => {
  if (c.lat !== undefined && !Number.isFinite(c.lat)) { droppedEndpoints++; return false; }
  ...
});
droppedEndpoints += beforeValidate - customers.length;   // counts the same rows again
```

Import a session with two bad endpoints and the toast reports four.

**Fix:** keep one counting mechanism. The length difference is the more robust of the two.

**Test:** import a fixture with a known number of invalid endpoints, assert the toast text contains
the correct count.

### G2. The dropped-items warning is never seen

**Where:** `handleImport()`.

The function fires the "N item(s) dropped" toast, then a few lines later fires
`showToast("Session imported successfully!")`. `showToast` is a singleton on a three-second timer,
so the second message replaces the first immediately. The user is told the import succeeded and is
never told that part of their data was discarded.

This is the same defect C2 was written to fix. C2 correctly merged the two *original* competing
toasts in this function, and then the success toast — which was always there — became the new
winner. The merge was done without checking what else in the function calls `showToast`.

**Fix:** one terminal toast. When items were dropped, the success message must carry that fact:
`"Session imported — 3 item(s) dropped as invalid"`, styled as a warning.

**Test:** import a fixture with invalid entries, wait for the toast to settle, assert the visible
text mentions the drops.

**While you are here:** grep the whole file for functions containing more than one `showToast`
call on the same path. C2 fixed two instances and this audit found a third. There may be more, and
each one silently discards a message the app decided the user needed.

### G3. Endpoints with no `lat`/`lng` survive import and then blank the endpoint list

**Where:** `handleImport()` validation, surfacing in `renderCustList()`.

The B4 filter only drops an endpoint when `lat`/`lng` are **present and non-finite**:

```js
if (c.lat !== undefined && !Number.isFinite(c.lat)) { ... return false; }
```

An endpoint with no `lat` key at all passes. `renderCustList()` then calls `c.lat.toFixed(2)`,
which throws, which aborts the whole `innerHTML` assignment — so the entire endpoint list renders
empty, not just the bad row.

This is precisely the failure B4 was written to prevent; the guard was written one condition too
narrow.

**Fix:** drop any endpoint whose `lat` or `lng` is not a finite number, absent included. Fold into
the G1 count.

**Test:** import a session containing one endpoint with no `lat` key. Assert the remaining
endpoints still render and the count is correct. Confirm the test fails before the fix — it should
produce an empty `#cust-list`.

### G4. `updateOnboardingFinancials()` still fires two toasts in a row

**Where:** `updateOnboardingFinancials()`.

C2 named this function explicitly and it was not changed. The margin clamp and the contingency
clamp still fire consecutive `showToast` calls, so a user who enters an invalid value in both
fields sees only the contingency message.

**Fix:** collect both conditions, emit one message. `"Margin clamped to 0–99%; contingency cannot
be negative."` when both fire.

### G5. A non-numeric margin writes the literal string `NaN` into the input box

**Where:** `updateOnboardingFinancials()` and `computeOnboardingFinancials()`.

`parseFloat('abc')` returns `NaN`. `computeOnboardingFinancials` does not clamp it, because
`NaN >= 100` and `NaN < 0` are both false — `NaN` escapes both guards untouched. Back at the call
site, `result.margin !== ob_margin` is **true** (`NaN !== NaN`), so the code takes the
clamp-writeback branch, writes `NaN` into `#ob-margin`, and shows "Margin clamped to 0–99%".

The price is then computed with `marginMultiplier = 1 - NaN/100` = `NaN`, which fails the
`marginMultiplier > 0` check and silently falls through to `customerPrice = internalCost` — a
quote with no margin applied at all, presented as if it were correct.

**Fix:** in `computeOnboardingFinancials`, coerce non-finite margin and contingency to 0 before
clamping. This is a pure function with existing unit tests — add the cases there, not in Playwright.

**Test:** `computeOnboardingFinancials({ totalHours: 100, rate: 100, marginPct: NaN, contingencyPct: 0 })`
must return `margin: 0`, not `NaN`.

### G6. Margin 99.5 is accepted while the toast claims the range is 0–99

**Where:** `computeOnboardingFinancials()`.

`if (margin >= 100) margin = 99;` is the only upper guard, so 99.5 passes and multiplies the
customer price by 200.

**Decision, small:** either clamp to 99 for anything above it, or change the message to state the
real bound. Clamping is the better answer — a 99.5% margin is not a number anyone means to type —
but note it either way rather than leaving the message and the behaviour disagreeing.

## 4. Task H — Export correctness

Two decisions and two fixes. **The decisions are Sanjoy's, not the agent's.** Present the
trade-off, take the answer, then implement.

### H1. DECISION — every exported phone number carries a stray apostrophe

**Where:** `csvCell()` in `src/core/format.js`.

The formula-injection guard prefixes an apostrophe to any value starting with `= + - @ tab CR`.
UK numbers start with `+`. So `+447700900123` exports as `'+447700900123`, on every row, in both
the From and the To columns.

Verified by running the function directly:

```
csvCell('+447700900123')  →  "'+447700900123"
```

**The trade-off is real, which is why this is a decision and not a fix:**

- Excel does begin formula parsing on a leading `+`, so the guard is not paranoid
- But the guard is currently damaging the primary content of every export, and anyone running a
  downstream script on the From/To columns has to strip the apostrophe

**Options, roughly in order of effort:**

1. **Guard `+` and `-` only when not followed by a digit.** `+44…` and `-5` pass clean;
   `+cmd`, `-cmd`, `=…`, `@…` stay guarded. Small regex change, keeps the protection where it
   matters. *This is the recommendation.*
2. **Pass known-numeric columns through an unguarded variant.** More precise, more code, and the
   custom-column feature means the "known" set is not fixed.
3. **Accept the apostrophe and document it** in `FEATURES.md` in user language. Zero risk, but the
   exports stay slightly wrong forever.

Whichever is chosen, the existing `csvCell` unit tests in `src/core/format.test.js` assert the
current behaviour for `+cmd` — update them deliberately, and add a case for `+447700900123`.

### H2. The CSV summary lines are unquoted and contain commas

**Where:** `exportGapData()`, the non-pair branch.

`breakdownLine` and `pairLine` are built by string concatenation and pushed into `csvRows` raw:

```js
'Invalid breakdown: ' + ... .map(([r,c]) => r + ' ×' + c).join(', ')
```

The `join(', ')` puts commas inside a single logical CSV field. In Excel, `malformed ×7, non-uk ×3`
spills across three columns and shifts everything after it.

B3 fixed the header row and the data rows. These two lines sit between them and were missed.

**Fix:** wrap both through `csvCell()`.

### H3. DECISION — the non-UK country code display is wrong for `+1`

**Where:** `validateUKNumber()` in `src/auditor/validate.js`.

C4 took the spec's fallback option — cap the display at two digits. Verified by running it:

```
+33123456789   →  "Non-UK destination (+33)"   correct, by luck
+8801712345678 →  "Non-UK destination (+88)"   wrong, Bangladesh is +880
+12125551234   →  "Non-UK destination (+12)"   wrong, US/Canada is +1
```

The original complaint was `+331` for France. Two digits fixes France and breaks North America,
which is the most common non-UK destination in most call data. The code comment claims it
"matches longest known prefix" — it does not; there is no prefix list. **Correct that comment
regardless of which option is chosen.**

**Options:**

1. **Drop the code from the label.** `"Non-UK destination"`, with the full cleaned prefix in the
   `title` tooltip. Cannot be wrong, loses a little information. *Recommendation if Sanjoy wants
   this closed today.*
2. **Add a real prefix table.** Roughly forty entries covers the realistic destination set;
   longest match wins. Correct, and the table is a maintenance item that will quietly go stale.
3. **Leave it and document the limitation.** Acceptable only if the chip is about to be redesigned
   in Phase 3 — check before choosing this.

Note that the reason string feeds `gapReasonBucket()`, which matches on `'non-uk'`. Any change to
the label must keep that match working, and the existing `validate.test.js` cases must be updated
in the same commit.

### H4. `exportOnboardingCSV()` duplicates the financial arithmetic

**Where:** `exportOnboardingCSV()`.

D3 extracted `computeOnboardingFinancials()` and `updateOnboardingFinancials()` uses it. But
`exportOnboardingCSV()` still computes contingency hours, billable hours, internal cost and
customer price inline, with its own copy of the formulas.

The two agree today. They will not agree after G5 and G6, because those change the clamping and
the export path will not receive it — so the screen and the exported quote will disagree on price.

**Fix:** call `computeOnboardingFinancials()` and use its result. Do this **after** G5 and G6, and
add an assertion that the exported customer price matches the value shown in `#ob-customer-price`.

| `financials.js` | **Done**, with six real unit tests |
| Characterisation tests before refactoring | **Not done** for either D1 or D2 |

The commit message for D2 says "prepare computeCoverage for extraction" and `SPEC.md` invariant 6
still correctly reads "DOM-free but not pure". **Nothing here is misrepresented** — the work simply
stopped halfway, and the repo says so honestly. That is a much better position than the changelog
in F2.

**Two things are worth knowing before deciding.** `computeCoverage()` is not yet extractable as
written:

- It **mutates its input**: `customers.forEach((c, i) => { c.idx = i; })` writes onto the caller's
  objects, which are the module-level `customers` array. Invariant 6 cannot become "pure" until
  this stops.
- It still has a **hidden dependency**: `findNearestRegionIdx()` is called from module scope and
  reads the module-level `regions`, so `input.regions` is not the only source of region data.

**The decision for Sanjoy:** finish D in this phase, or defer it to its own phase and say so in
`claude_memory.md`.

Deferring is defensible. The valuable half — the `pairKey` deduplication and the memo-key fix —
already landed. What remains is structural work with no user-visible benefit, and it competes with
Phase 3, which does have one. **The audit's suggestion is to defer, complete F1 by deleting
`pairing.test.js`, and record the deferral explicitly** so the next agent does not find a
half-extracted `computeCoverage` and guess at intent.

What is **not** acceptable is leaving it undecided. A function whose signature says "pure" and
whose body mutates its arguments is worse than one that never pretended.
